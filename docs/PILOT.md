# Пилот на одной линии: 4–6 недель

Документ для заказчика и для команды: что нужно от завода, что мы делаем по неделям, как поймём, что пилот удался, и какие есть риски. Опирается на то, что уже есть в репозитории (`docs/PROGRESS.md`, `docs/ARCHITECTURE.md`); то, чего ещё нет, помечено явно (раздел 8).

## 1. Цель и рамки

**Цель.** За 4–6 недель на одной линии показать, что двойник на **реальных** данных завода (а не виртуальных) считает KPI так же, как заводские отчёты, находит потери, которые не видны в Excel, предупреждает об остановках и риске невыполнения плана, и делает это безопасно для OT.

**Что получает завод к концу пилота:**
- живая схема линии, состояние оборудования и буферов, отклонения и инциденты;
- KPI по ISO 22400 (A, E, QR, OEE, FPY, MTBF, MTTR) по сменам, дереву потерь в минутах, машинах и тенге;
- сверка источников: журнал простоев против потерянного времени, баланс потока, план против цели;
- оповещения с эскалациями (интерфейс, Telegram), андон и классификация причин простоя с планшета оператора;
- прогноз выполнения плана месяца с вероятностью, what-if и рычаги с эффектом;
- сменный рапорт, где каждое число проверено по данным;
- предиктивное ТО — в той мере, в какой хватит данных (см. нед. 5–6);
- итоговый отчёт: сверка с вашими отчётами, найденные потери, эффект в машинах и ₸ на реальных ценах, план масштабирования.

**Какую линию выбрать.** Критерии: есть OPC UA/SCADA со статусами и счётчиками; заметные потери; готовый «чемпион» среди мастеров. Рекомендация для данных кейса: Окраска-1 (чаще всего узкое место, самый высокий брак) вместе со счётчиками выпуска соседних линий и уровнями буферов BIW/PBS, чтобы работал баланс потока. Окончательный выбор делаем на нед. 0.

**Что не входит.** Управление оборудованием и запись в контроллеры; интеграция с ERP/MES «в обе стороны» (только выгрузки файлов); SSO/AD; 3D-сцена; мультизаводская конфигурация; мобильное приложение. Это P2 (SPEC §1.4), в пилот не входит.

## 2. Что нужно от заказчика

### 2.1 Доступ к OT (только чтение)

| Что | Подробности | Зачем |
|---|---|---|
| OPC UA-сервер SCADA или шлюза | адрес и порт, политика безопасности (рекомендуем `Basic256Sha256`, `SignAndEncrypt`), обмен сертификатами | единственный канал данных из OT |
| Учётная запись OPC UA **только на чтение** | права: Browse, Read, Subscribe; **без Write и Call** | гарантия «только чтение» (раздел 6) |
| Список тегов линии | NodeId, тип, единицы, диапазон, период обновления: состояние/статус, код аварии, счётчики выпуска/годных/брака, время цикла, телеметрия (ток, температура, вибрация, давление), уровни буферов | заполнение `config/tag_map.yaml` |
| Расшифровка статусов | какие значения тега состояния что означают (работа, простой, авария, ожидание, плановое ТО) | отображение на 8 состояний модели |
| Брокер MQTT (если есть Unified Namespace) | адрес, учётка на подписку | события единиц и дефектов (без MQTT коды дефектов придут только с терминала оператора, см. раздел 8) |
| Контакт инженера SCADA/автоматизации | на время пилота, отзывчивость в течение рабочего дня | согласование тегов, диагностика |
| Если OPC UA нет | OPC UA-шлюз или экспорт из SCADA, предоставляемый заказчиком | наш коллектор читает только OPC UA и MQTT |

### 2.2 Данные MES и Excel (в исходном формате)

- Выгрузки в формате кейса: отчёт по линиям и сменам (план, факт, брак, время работы, загрузка), журнал простоев (оборудование, причина, минуты, дата, по возможности время начала), план по моделям, таблица качества. Минимум последний месяц, лучше 3–6 месяцев. Принимаем `.docx`, `.xlsx`, `.csv`; шаблон — `GET /api/v1/import/template.xlsx`.
- Текст «дополнительных вводных»: цели и ограничения (OEE не ниже, брак не выше, лимит простоя, плановый выпуск); мы сравниваем их с конфигом и показываем расхождения.
- Справочники: перечень оборудования линии с классом критичности (A — нет резерва, B — есть обход с долей мощности, C — не влияет), коды причин простоя и дефектов, которыми пользуются сейчас, календарь смен и праздников, идеальный такт по моделям, ёмкость буферов, число постов доработки.
- Архив телеметрии из historian SCADA за 3–6 месяцев — **желательно**, нужен для обучения предиктивных моделей (нед. 5–6); без него модели обучаются только на накопленных за пилот данных.

### 2.3 Один сервер

| Параметр | Значение |
|---|---|
| Размещение | on-prem, сегмент DMZ (раздел 6) |
| Платформа | Linux x86_64 или arm64, Docker и Docker Compose |
| Ресурсы | 8 ядер, 16 ГБ ОЗУ (эталон демо), SSD не менее 256 ГБ (оценка; уточним по числу тегов на нед. 2) |
| Сеть | исходящее: только к OPC UA-серверу (и MQTT-брокеру, если есть); входящее: HTTPS из IT-зоны на web/api, SSH с jump-хоста администратора; интернет не нужен |
| Прочее | синхронизация времени по NTP (на сервере и на стороне SCADA); внутренний DNS-имя и TLS-сертификат для web; GPU не нужен |

### 2.4 Люди и время

| Роль | Участие |
|---|---|
| Спонсор (директор производства) | старт, еженедельный 30-минутный статус, решение о масштабировании |
| Владелец пилота на стороне завода | ежедневный контакт, доступ к людям и данным |
| Инженер SCADA/автоматизации | нед. 1–2: теги и доступ; дальше по запросу |
| ИТ/ИБ | нед. 0–2: сервер, сеть, согласование зон и каналов |
| Мастер смены («чемпион») | нед. 3–6: сверка KPI, подтверждение причин простоев, обратная связь |
| Служба ТОиР и качество | нед. 4–6: оповещения, наряды, брак |
| Операторы линии (2–3 человека) | нед. 5: обучение на планшете (≈ 1 час) |

Не нужно: доступ на запись в контроллеры, исходные тексты программ ПЛК, интернет, облако, персональные данные сотрудников сверх имён пользователей и ролей.

## 3. План по неделям

**Нед. 0 (подготовка, до старта).** Подписание NDA и условий, выбор линии, заявка на сервер, согласование зон и каналов с ИБ (раздел 6), создание OPC UA-учётки только на чтение, запрос выгрузок MES и справочников.

| Неделя | Что делаем | Результат (контрольная точка) | От заказчика |
|---|---|---|---|
| **1. Карта тегов и модель** | Установка на сервер (`docker compose --profile prod`), `CLOCK_MODE=system`, смена секретов. Разбор справочников: заполнение `config/plant.yaml` (линия, оборудование, критичность, такты, буферы, смены) и `reason_codes`/`defect_codes`. Составление `config/tag_map.yaml` по списку тегов. **Импорт выгрузок MES** — первые находки «за секунды» (KPI, сверка, оповещения по их же данным) | двойник запущен; `make config-check` зелёный; отчёт импорта по истории; первый список расхождений в данных | список тегов, расшифровка статусов, выгрузки, справочники; мастер на воркшоп 2 часа |
| **2. Коллектор в DMZ** | Подключение коллектора к OPC UA на чтение, режим безопасности `SignAndEncrypt`, проверка тегов (неизвестные значения → DQ-07 → правка карты). Проверка часового пояса и NTP. Проверка store-and-forward: отключить сеть на ≈ 1 час, убедиться, что события досылаются без потерь и дублей. Сетевая проверка «только чтение» (раздел 6). К концу недели — **живые данные линии** на `/live` | живые состояния, счётчики, буферы; нет новых неизвестных тегов за сутки; тест обрыва связи пройден; подтверждение ИБ: нет операций записи | сервис Browse/Read для проверки; окно для теста обрыва связи |
| **3. Калибровка на реальных данных** | Первая калибровка параметров модели по накопленным дням: интенсивность отказов, длительности ремонтов, эффективность линии, доля брака (`GET /calibration`: для каждого параметра видно, из данных он или из априора). Подстройка порогов (OEE, брак, лимит простоя) в `config/rules.yaml`; переопределения через `PATCH /api/v1/config/thresholds` движок на лету пока не применяет (раздел 8). Пересчёт прогноза месяца | калибровка v1; прогноз месяца на реальных данных; список параметров, где данных ещё мало | мастера и технологи: проверка «похоже ли на правду» |
| **4. Валидация KPI против ваших отчётов** | Параллельная работа 5 рабочих дней: сменные KPI двойника против заводских отчётов (A, E, QR, OEE, выпуск, брак, простои). Каждое расхождение разбираем и фиксируем: разные определения, время, ручные поправки, ошибки тегов. Повторная калибровка. **Контрольная точка 4 недель** | протокол сверки KPI; журнал расхождений; решение «продолжаем» | отчёты смен за эти 5 дней; мастер подтверждает/оспаривает |
| **5. Оповещения и терминал** | Правила оповещений (AL-S1, AL-D1, AL-Q1 и др.), каналы и цепочка эскалации под ваши роли; Telegram (если разрешены внешние вызовы — иначе только интерфейс); планшеты операторов: андон, причины остановок, ввод дефектов; обучение (≈ 1 час на смену); сменные рапорты | оповещения приходят адресатам; операторы классифицируют простои; рапорт смены проверен мастером | планшеты/ноутбуки в цехе, Wi-Fi в зоне линии; список адресатов и PIN-ролей; 2–3 оператора |
| **6. ML и итоги** | Предиктивное ТО: если есть архив телеметрии и журнал отказов — переобучение LightGBM на ваших данных, model card, сравнение с правилами по сигналам; иначе — сбор данных и режим «в тени» (прогноз выхода сигналов за предел по Тейлу — Сену не требует обучения). Пересчёт эффекта на реальных цене и марже. Итоговый отчёт и демонстрация | итоговый отчёт: сверка KPI, топ-3 потерь в машинах и ₸, точность прогноза против факта, метрики моделей на реальной истории, план масштабирования | решение спонсора; согласование формулировок отчёта |

**Вариант на 4 недели:** нед. 1–4 как выше; оповещения и терминал запускаются в сокращённом виде на неделе 4 (интерфейс и один адресат, планшет на одной смене); ML и итоги переносятся в «фазу 2» (6+ недель).

**Накопление данных.** Живые данные начинают идти в конце нед. 2, поэтому окно калибровки в 20 рабочих дней (`window_days`) заполняется к концу нед. 6. До этого часть параметров берётся из априорных оценок и помечена в интерфейсе. Нужные для предиктивной модели отказы редки; сколько их накопится за 4 недели, зависит от оборудования. Метрики моделей на реальных данных мы заранее не обещаем.

## 4. Критерии успеха

Предлагаемые значения; согласовываем и фиксируем в начале нед. 1.

| Область | Критерий | Как измеряем |
|---|---|---|
| Данные | в рабочие смены ≥ 99 % времени есть живые данные линии; новых неизвестных тегов (DQ-07) нет после нед. 2 | счётчики коллектора, DQ-07 |
| Надёжность | при обрыве связи с БД или сетью до 24 ч события не теряются и не дублируются | тест на площадке (по образцу T-SF), число событий опубликованных = в БД |
| Скорость | изменение состояния оборудования видно на экране ≤ 2 с (p95) | замер на площадке |
| KPI | расхождение с заводскими отчётами по A, E, QR, OEE не более 1 п.п., по выпуску не более 1 % в ≥ 90 % смен за 5 рабочих дней; все расхождения объяснены | протокол сверки (нед. 4) |
| Использование | ≥ 80 % простоев длиннее 5 мин получили причину к концу смены (автоматически или оператором); мастер использует экран вместо ручного сбора минимум в 3 из 5 смен | интерфейс, опрос мастера |
| Оповещения | остановка класса A → оповещение ≤ 2 с; доля оповещений, которые мастера сочли ложными, < 20 % | журнал `alert`, опрос |
| Прогноз | ошибка P50 недельного/месячного прогноза против факта ≤ 5 %; факт попадает в P10–P90 примерно в 80 % случаев (на виртуальном заводе покрытие 70–75 %) | сравнение прогноза и факта |
| Безопасность | в журнале SCADA/OPC UA заказчика нет операций записи и вызовов методов от учётки двойника | аудит ИБ |
| Бизнес | топ-3 потерь оценены в минутах, машинах и ₸ на реальных данных; эффект пересчитан на реальных цене и марже; принято решение о масштабировании | итоговый отчёт |

## 5. Риски и меры

| Риск | Мера |
|---|---|
| Согласование ИБ и доступа занимает больше времени | начинаем на нед. 0; пока доступа нет, получаем ценность из файлов: импорт выгрузок даёт KPI, сверку и оповещения без OPC UA |
| Нет OPC UA (закрытые протоколы ПЛК) | шлюз или экспорт из SCADA на стороне заказчика; коллектор читает только OPC UA и MQTT |
| В тегах нет явных состояний, только счётчики и биты аварий | согласуем вывод состояний из статусов и битов аварии на воркшопе нед. 1; режим «единицы по счётчикам» не реализован (раздел 8) — потребуется доработка |
| Расхождение определений (смена, простой, брак, время работы) | воркшоп нед. 1, фиксируем в конфиге; журнал расхождений на нед. 4 |
| Нагрузка на OPC UA-сервер заказчика | начинаем с небольшого списка тегов, период публикации берётся из карты тегов (в примере 500 мс), по согласованию с инженером SCADA |
| Рассинхрон времени между SCADA и сервером | NTP на обеих сторонах; в событиях храним время источника и время получения; проверка на нед. 2 |
| Мало отказов для обучения ML | правила по сигналам и прогноз выхода за предел работают без обучения; модели переобучаются по мере накопления; метрики не обещаем |
| Операторы и мастера не пользуются терминалом | «чемпион»-мастер, минимум нажатий, крупные кнопки, офлайн-очередь действий, обучение на нед. 5, опрос после недели работы |
| Объём данных больше расчётного | хранение сырых данных 30 дней, сжатие через 7 дней, спул 2 ГБ; оценка объёма на нед. 2 и корректировка диска |
| Казахский интерфейс — черновой перевод | проверка носителем на нед. 1–2, если нужен казахский |
| Одна реплика API (блокировка подбора паролей и WebSocket-хаб в памяти) | для пилота одной линии допустимо; для масштабирования вынести состояние в Redis |

## 6. Безопасность

### Принципы

- **Только чтение из OT.** В коде коллектора нет вызовов записи (тест T-RO блокирует коммит), клиентская сессия создаётся учёткой только на чтение, межсетевой экран пропускает только исходящее соединение коллектора на порт OPC UA. Выключатель: остановка коллектора или закрытие правила на межсетевом экране отрезает двойник от OT; контроллеры от двойника не зависят.
- **Зоны и каналы IEC 62443.** OT (PLC, SCADA) — DMZ (сервер двойника) — IT (пользователи). Каналы: C1 коллектор → OPC UA (чтение); C2 браузеры → HTTPS на web/api; C3 интернет (по умолчанию закрыт); C4 загрузка файлов человеком. Схема и таблицы — `docs/ARCHITECTURE.md`, раздел 6. Целевой уровень SL-T для DMZ предлагаем SL 2 и уточняем по вашей оценке рисков; сертификации по IEC 62443 у продукта нет.
- **On-prem.** Все данные остаются на сервере заказчика. Облако не используется.
- **Офлайн.** `OFFLINE=true`: ни одного внешнего HTTP-вызова. Рапорты — шаблоном или локальной моделью; Telegram отключён. Внешние вызовы включает только заказчик, с перечнем разрешённых хостов на межсетевом экране.
- **Доступ и аудит.** Роли (директор, мастер, оператор, ТОиР, качество, администратор), проверка роли на каждом маршруте, JWT 12 ч, пароли argon2id, ограничение подбора пароля, журнал `audit_log` на любое изменение данных, ошибки в формате RFC 7807, логи с `trace_id`.

### Что меняется при переходе с демо на пилот (чек-лист администратора)

| Пункт | Действие |
|---|---|
| Профиль | `docker compose --profile prod` (без виртуального завода `sim`; поле `Degradation` недоступно физически) |
| Секреты | сменить `JWT_SECRET` (по умолчанию `change-me`), `DEMO_PASSWORD`, пароль БД; удалить или перепаролить демо-пользователей, завести реальных; PIN-коды Telegram |
| Часы | `CLOCK_MODE=system` |
| Карта тегов | `config/tag_map.yaml` с адресом OPC UA-сервера и режимом `SignAndEncrypt`; сертификат и ключ клиента коллектора |
| MQTT | пароль и TLS на брокере (в демо анонимный доступ) |
| TLS | reverse proxy перед web/api с сертификатом заказчика (в демо-сборке TLS нет) |
| CORS и ссылки | `CORS_ORIGINS`, `PUBLIC_WEB_URL` по реальному адресу |
| Резервные копии | `pg_dump` по расписанию на хранилище заказчика (готового скрипта пока нет, настроим на нед. 1) |
| Обновления | образы передаются в закрытый периметр (`docker save` / `docker load`), откат — предыдущий образ |
| Сеть | правила межсетевого экрана по каналам C1–C4; запрет любых соединений из OT в DMZ |

Известные ограничения безопасности: JWT без отзыва до истечения токена; состояние защиты от подбора паролей в памяти одного процесса; образы не проходили сканирование уязвимостей.
